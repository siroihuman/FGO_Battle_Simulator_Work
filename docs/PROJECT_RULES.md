# プロジェクト必須規則

仕様書バージョン: 1.0.0

この文書は作業開始時に確認する短縮版です。数値、順序、例外の正確な定義は依頼に関係する [specs/](specs/) を正本として参照します。

## 優先順位

1. 現在のユーザーによる明示指示
2. project-manifest.json とこの文書
3. 詳細仕様
4. 決定記録
5. 実装状況

チャット履歴や記憶だけを根拠に実装しません。

## 戦闘の範囲

- 完全戦闘形式。最終Waveの敵全滅で勝利、味方全滅で敗北、同時全滅は敗北。
- 特殊勝利条件・特殊敗北条件は追加しない。最大3Wave。
- 味方は前衛3騎必須、控え0〜3騎。同一サーヴァントの重複を許可する。
- 敵は全Wave合計1〜99体、同時出現3体または6体、ブレイクは最大10ゲージ。

## 実装の不変条件

- 戦闘は味方行動、味方ターン終了、敵行動、敵ターン終了の順に進め、Wave・勝敗は終了処理の完了後だけ判定する。
- 死亡、交代、敵補充は、1行動の全Hitと効果が終わった安全な境界でだけ処理する。
- 戦闘データIDと戦闘個体IDを分離し、重複編成でもHP、NP、状態、CT、Lv、装備を個別に保持する。
- 同じシード、設定、操作なら、結果と乱数消費順を完全に再現する。
- 中断保存は味方入力待ちまたは終了済みの境界でのみ行い、再開は保存済み状態と全乱数列位置を直接復元する。リプレイ不一致や保存形式不一致を近似して続行しない。
- UI・ログはエンジンの確定結果を使い、戦闘計算や状態遷移を再実行しない。
- UIの状態合算は付与中の同種・同条件の登録値を表示用に正負加算するだけとし、倍率のpermilleは表示時だけ百分率へ変換する。期限・回数・解除・戦闘結果を変更しない。
- 確定結果演出はチェイン、確定HP・味方NP増減、ターン終了、Wave突破を利用者の前後操作で表示し、途中状態を保存・リプレイの正本にしない。攻撃数値は確定行動ログの対象別総ダメージ、各バーは確定前後状態を使い、HP差分からダメージを算出しない。
- カードのクリティカル表示は保存済みスター配分へQuick始動・Mightyの20%を表示用に合算するだけとし、100%を上限にする。Quick先頭は1枚目選択時点から表示し、解除・先頭変更で戻すが、実判定・乱数・保存済み配分を変更しない。
- 能動カード再配布は味方入力境界・カード3枚提出前だけ使用し、現在前衛の全通常カードから新周期の5枚を配る。宝具カードを混ぜず、`commandStars`／`nextCommandStars`を変更せず、新手札のカード別スター配分をエンジンで確定・保存する。
- カード再配布を含む操作の不正・候補不足・未対応は、状態、CT、履歴、ログ、乱数を変更する前に原子的に拒否する。

## 効果とデータ

- 通常処理は共通効果、限定的例外処理は共通トリガー、固有例外処理だけは対象別モジュールで扱う。
- 未対応または不明な効果を近似しない。能動行動は状態・NP・敵チャージ・乱数を変える前に全体を不発とする。
- 魔術礼装・概念礼装の選択は初回カード配布前に1回だけ解決し、概念礼装のATK・HPは戦闘個体別、開始時効果は既存の共通受動効果として適用する。未対応開始時効果は状態・採番・乱数変更前に拒否する。
- 初期概念礼装はカレイドスコープと黒の聖杯の最大解放・星5Lv100固定とする。各味方戦闘個体0～1枚、未選択可、同一礼装の複数個体装備可とし、所持枚数は管理しない。
- カレイドスコープは装備者の開始NPを100%増加し、黒の聖杯は装備者へ解除不能の宝具威力80%アップと毎ターンHP500減少を付与する。黒の聖杯のHP減少はHP0可能で、HP1停止のスリップ精算へ近似しない。
- 初期敵は`radiant-arm-of-dawn-saber`（黎明の炎腕・剣）1種と、剣基準の極級3 Wave・7個体とする。再利用敵定義と、Wave・戦闘個体ID・Lv・HP・ATK・配置を分離する。
- 初期敵のランダム単体対象と通常攻撃クリティカルは用途別乱数列を使い、敵ターン終了時の通常チャージ増加は生存前衛だけを1増加する。控えとチャージ攻撃未設定敵は進行させない。
- やけど・毒・呪いは`slip_damage`の種類として延焼・蝕毒・呪厄だけに対応し、発動時の同種倍率を固定して種類別合計後にpermille倍率を掛け、小数点以下を種類ごとに切り捨てる。対応外スリップとHP0可能なHP減少は倍加しない。
- サーヴァントは強化後の現行データのみ、上位スキル3つ、上位宝具1つ、全クラススキルを資料順に登録する。ページ番号を内部IDにしない。
- 再臨段階で名称・スキル・宝具が変わる場合も、共通の再臨段階選択を実装するまではユーザー指定の段階だけを現行定義として登録する。今回は最終再臨を採用し、段階ごとの別サーヴァント定義や個別選択UIを追加しない。
- 編成の公式／オリジナル区分は登録時の明示リストを使い、各区分内をゲーム内通し番号の数値昇順にする。名称やURLから区分を推測せず、タブ閲覧だけで現在選択を解除しない。
- 登録済みサーヴァントのWiki導線とスキル・宝具説明は定義へ保存した参照URL・登録値だけを使う。保有スキル説明は実装対象のLv10倍率だけを表示し、宝具の宝具Lv別・OC別倍率は維持する。未登録URLや倍率をUIで推測しない。
- 通常の確率・倍率は整数permilleを使う。資料値が0.1%刻みに収まらない場合は丸めず、該当する共通修正値だけを0.01%単位の明示型で追加し、既存の整数permille乱数経路を変更しない。
- スキル・宝具の弱体デメリット状態は資料に個別率がない限り基礎付与率500%を明示登録し、通常の弱体耐性・弱体無効判定を通す。
- 固定値、宝具Lv別、OC別の値を区別する。単体対象は実行時に検査する。
- 敵宝具の宝具LvとOCは戦闘個体・宝具行動ごとの明示値だけを使い、敵Lv、現在／最大チャージ、ターン、Waveから推定しない。段階値を使う行動は開始前に必要文脈と5段階値を一括検査し、欠落・不正・未対応なら固定値へ近似せず、状態・チャージ・効果採番・乱数変更前に全体を不発とする。
- 味方・敵のターン終了トリガーによるスター獲得は、どちらもプレイヤーの次回味方コマンド用へだけ資料順に加算し、各加算時点で99個を上限とする。現在使用分への指定、控え中の発動、終了処理やUIでの再計算を許さない。

## 検査と更新

- 変更範囲の回帰テストを追加し、npm test、npm run typecheck、npm run build を実行する。
- コア規則・データ形式を変えた場合は project-manifest.json、挙動を変えた場合は該当仕様書、進捗を変えた場合は IMPLEMENTATION_STATUS.md と START_HERE.md を同じPRで更新する。
- 新しい方針は DECISION_LOG.md に短く記録し、詳細な理由や完了履歴は [archive/](archive/) へ保存する。
